# Rules That `wbfy` and `wb` Expect of Target Repositories

`wbfy` is a re-configuration tool: its input is almost always what `wbfy` itself generated in a previous run.
Both tools therefore support exactly one canonical format per file and one canonical repository layout.
A repository that deviates from these rules is fixed manually (or by re-running `wbfy`); the tools do not add code to accommodate deviations, and they may fail fast or overwrite deviating files with canonical output.

## Repository preconditions

- Bun at or above the pinned minimum version is installed; `wbfy` aborts otherwise.
- The target directory has a `package.json` (or another supported manifest such as `poetry.lock`, `uv.lock`, `go.mod`, `pom.xml`, `pubspec.yaml`).
- Monorepos place workspaces under `packages/*` and/or the patterns declared in the root `package.json` `workspaces` array.
- Every managed file is a regular in-repository file: symlinks and paths resolving outside the repository are refused.
- Git dependency specifiers in `package.json` files may point only at `WillBooster/*` or `WillBoosterLab/*`; anything else aborts the run (other ecosystems' manifests are not checked).
- The wbfy badge in `README.md` records the applied `wbfy` version and is the idempotency marker; do not edit or remove it.
- Package managers are up to date, because the organization's minimum-release-age policy is silently ignored by older ones: npm >= 11.10 for the gate and >= 11.17 for its exclusion list, Yarn Berry >= 4.10.3, and Bun >= 1.3; the machines' global `~/.npmrc`, `~/.yarnrc.yml` and `~/.bunfig.toml` are machine-managed by every `wbfy` run, or on their own by `wbfy apply-release-age-gate` (only registry settings survive in the first two, and only in `~/.npmrc` on developer machines).
- Tool versions are pinned in `mise.toml`; environment variables and secrets live in `fnox.toml`, never in `.env*` application files — the sole exception is `.env.cloudflare`, a gitignored, untracked file holding Cloudflare deploy credentials; `bunfig.toml` uses Bun's isolated linker; `bun.lock` carries no Takumi Guard (`npm.flatt.tech`) URLs in its `resolved` fields (explicit direct tarball dependency URLs and legitimate scoped private-registry URLs such as Verdaccio's remain).

## File-format rules

- `package.json` must be strict JSON and is always rewritten via `sort-package-json`.
- `tsconfig.json`, `.vscode/settings.json`, and `pyrightconfig.json` must be JSONC; `.releaserc.json` strict JSON; workflows YAML mappings; `renovate.jsonc` is the only supported Renovate config location.
- Renovate `extends` entries use the canonical preset casing. Verdaccio `npmrc`, `npmrcMerge`, and `hostRules` settings live in the shared preset and Mend organization settings, not repository Renovate configs.
- Unparseable auxiliary configs (tsconfig, workflows, Renovate, VS Code, pyright) are skipped with a warning and never overwritten. Exceptions: an invalid `package.json` marks the target invalid and fails the run; `fnox.toml` parse or layout errors fail the run; an unparseable `mise.toml` is left untouched and only logged; an unparseable `.gemini/config.yaml` is replaced with the canonical config.
- `fnox.toml` layout is strict: an age provider named exactly `[providers.age]`, no `import`, no profile-specific providers, a root `fnox.toml` when a nested config declares its own age provider, and the file must be git-tracked. Development defaults live in `[secrets]`; `test`/`staging`/`production` overrides live in `[profiles.<mode>.secrets]`. `wb gen-docker-env` additionally rejects the top-level `env` and `default_provider` settings and the `json_path`/`line`/`as_file` value transformations on plaintext entries.

## Project structure expected by `wb`

- Source code lives in `src/`, scripts in `scripts/`, framework code in `app/`.
- Under `test/`, only `unit/`, `e2e/`, `debug/`, `helpers/`, and `fixtures/` may exist, and `*.test.*` / `*.spec.*` files only under the first three (fixture data under `test/fixtures/` and hidden entries are exempt); violations fail `wb lint` and `wb test`. A non-workspace-root package with its own `playwright.config.ts` must have `test/e2e/`; a workspace root may share a root-level `playwright.config.ts` while the e2e specs live in one app package.
- `package.json` scripts follow the `wbfy`-generated set (`typecheck`, `lint`, `test`, `test/ci`, `verify`, …); optional hooks such as `build`, `gen-code`, `deploy`, `deploy:staging`, `seed`, and `docker/build/prepare` are picked up by name.
- Generated commands use one form per target kind, in every context (package scripts, lefthook, Playwright `webServer`, CI steps): package scripts are invoked as `bun run <script>`, `node_modules` bins as `bun <bin>` (e.g. `bun wb lint`, `bun lefthook install`, `bun playwright install`), and tools outside `node_modules` (mise-managed `flutter`, `poetry`, `uv`, …) bare. Because `bun <name>` runs a package script of that name in preference to a bin, no package script may share its name with an installed bin.
- `WB_ENV` is one of `development` / `test` / `staging` / `production`; environment variables come from `fnox.toml` plus `mise env`.
- Docker apps have a `Dockerfile` whose container listens on port 8080 (the host port comes from `PORT`). When `PORT` is undefined, local `wb start`/`wb test` auto-select a free port (searched within 20000–32767 from a deterministic per-repository, per-`WB_ENV` preferred port); an undefined `NEXT_PUBLIC_BASE_URL` is derived from the resolved port (declared or auto-selected), so repositories define `PORT`/`NEXT_PUBLIC_BASE_URL` only where a fixed value is required. Every local `wb start`/`wb test` of a development or test environment (a pinned `PORT` included) records its server in the gitignored, wb-internal `<repository root>/.wb/server-<WB_ENV>-<package>.json` — the URL plus the publishing process's pid and start time, replaced by rename so the URL and the identity that validates it are never read apart. It is not an interface for other tools: a publication outlives its server, so reading the URL without re-checking that identity yields a dead address (or an unrelated process that took the port). Scripts get the URL from `wb run`, which exposes only a verified one. `wb run` exposes that URL as `NEXT_PUBLIC_BASE_URL` when nothing else defines it, so scripts that talk to the local app need no pinned `PORT` either — a configured value always wins, including a deliberately empty one. A publication counts only while its publisher is alive and its origin answers a connection (it is written before the server binds, so a non-answering one is ignored, never deleted, and never probed by binding — that would take the port from the server it asks about); a publication is never deleted, only overwritten by the next server of that package, because liveness already makes an outdated one inert while an exiting server cannot delete safely — it can always be preempted between checking ownership and unlinking, and would then remove the replacement a pinned-port restart just published. A script gets the server of the package it sits in (the nearest `package.json` above it, so a manifest-less `scripts/` directory counts as its package's); only a script belonging to no app — under the root package or no package at all — takes the single serving app, so a repository serving several apps never guesses. `wb dotenv` deliberately stays out of this: it is also the low-level runner wrapping server-starting commands, which must keep resolving their own port. Continuing the port rules: a `NEXT_PUBLIC_BASE_URL` that pins an explicit port, or that points at loopback at all (a portless loopback URL pins the scheme's default port), must pin the matching `PORT` too (wb fails fast otherwise). Fixed values remain required for deployed profiles and for profiles used to run Docker images: images bake only fnox-declared values (`wb gen-docker-env`) and containers receive only declared keys, so the auto-derived values never reach them. Dev servers must take their port from the `PORT` environment variable (Next.js does natively; vinext/wrangler receive `--port` from wb; Vite apps read it in their config).
- Docker images never contain an age identity in any form (no `FNOX_AGE_KEY` `ARG`/`ENV`, no key file): one leaked CI key decrypts every profile of the committed `fnox.toml`, including ciphertexts in Git history. Images bake only non-secret values — the canonical generator is `wb gen-docker-env`, producing the gitignored `.docker.env`; `wb optimizeForDockerBuild --outside` runs it automatically only when the Dockerfile consumes `.docker.env` and an `fnox.toml` exists (the `docker/build/prepare` hook remains for extra steps; on CI, `WB_ENV` must be exported, with `WB_SKIP_ENV_CHECK=1` as the opt-out) — and secrets are injected at runtime from the deployment platform's store. `.docker.env` is shell-sourceable single-quoted dotenv, sourced at build time via `set -a && . ./.docker.env` or read by a dotenv parser, NOT via `docker --env-file`, which keeps quotes literally; runtime entrypoints apply baked values only to keys the platform did not already set (e.g. via a `${KEY=...}`-style loop — colon-less, so a deliberately empty platform value survives — because a bare re-source would overwrite platform-injected values). Baked keys must be POSIX shell identifiers other than `__proto__`, and baked values must contain no apostrophe, CR/LF, trailing backslash, or expansion-sensitive `$` (bare `$NAME`, `$$`, `\$`, or an unresolvable `${...}`); plaintext-to-plaintext `${NAME}` references are resolved statically, matching fnox. A build-time decryption uses the BuildKit secret id `fnox_age_key`, consumed as `RUN --mount=type=secret,id=fnox_age_key,env=FNOX_AGE_KEY` and scoped to exactly the `RUN` that needs it, never during dependency installation; `wb`'s Docker entry points pass that secret whenever `FNOX_AGE_KEY` is set in their environment. Shipping fnox + `fnox.toml` for runtime decryption is allowed only for containers running exclusively first-party code; images that execute untrusted code must contain no fnox binary, no `fnox.toml`, and no age key. Dockerfiles never `COPY .env*` globs (a later `rm` does not remove a file from the layer that copied it). The generated `dist/bash/apply-docker-env.sh` applies `.docker.env` only to keys the environment did not already provide, then execs the given command — use it instead of hand-written merge loops. Litestream configs are generated with `wb db create-litestream-config --env-refs` (writes `${VAR}` placeholders Litestream expands from the runtime environment, so generation needs no secrets; at a monorepo root the command auto-selects the single project when every candidate resolves to the same database file), and `run-litestream.sh` fails fast when a `${VAR}` referenced by the config (default `/etc/litestream.yml`, overridable via Litestream's own `LITESTREAM_CONFIG`) is unset. `wb optimizeForDockerBuild --outside` also lints the Dockerfile the build resolves (the self project's, else the root's): an `ENV`/`ARG` age identity or a root `.env`/`.env.<mode>`/`.env*` `COPY` is always an error, and with a Railway build config (`railway.toml`/`railway.json` — `.railwayignore` alone is not a signal) every non-cache `RUN --mount` — including the `fnox_age_key` secret mount, which Railway-built images therefore cannot use — is an error because Railway's builder rejects it at Dockerfile validation time; `WB_SKIP_DOCKERFILE_LINT=1` is the escape hatch for repositories that keep a Railway config but build their image elsewhere. With `--env-refs`, a Drizzle project's `DATABASE_URL` must be a plaintext fnox default. A Railway Docker repository whose Dockerfile consumes `.docker.env` carries a `.railwayignore` containing `!.docker.env`; wbfy removes that rule when the Dockerfile no longer consumes the file.
- Cloudflare Workers use a `wrangler.jsonc`/`wrangler.json` config; `wb deploy` targets Workers only, requires `WB_ENV` of `staging`/`production`, and reads Cloudflare credentials from `.env.cloudflare` (gitignored and untracked). `.dev.vars` and `worker-configuration.d.ts` are generated, never hand-written, and `worker-configuration.d.ts` is never tracked in ANY package — in a package that consumes it, the file stays gitignored because the `wb gen-code` postinstall regenerates it deterministically from committed inputs alone (the wrangler config plus the `fnox.toml` key names via `wrangler types --env-file`), so local `.dev.vars`/`.env*` files never affect it and wbfy's management decision must likewise never depend on such machine-local files; in a package that opted out of the managed generation, wbfy deletes a stray copy as disposable generated output. The `/worker-configuration.d.ts` ignore rule itself is wbfy-owned: never add it to the `.gitignore` head/tail user sections. `wb gen-code` is the only supported worker-types generator; wbfy rejects every direct `wrangler types` invocation before changing repository files.
- Declare locally served D1 bindings at the wrangler config's top level and keep their migration layouts aligned with each `env.<name>` copy: local `wb start`/`wb test` and `wrangler dev` use the top level, while deploy resolves the selected environment. wb selects wrangler-native migrations for an explicit `migrations_pattern` or flat `*.sql` files in `migrations_dir`; otherwise a D1-targeting drizzle config selects drizzle-kit. When such a drizzle config is present, mixing native and non-native layouts across bindings or declaring multiple drizzle-managed D1 bindings is unsupported and aborts local start/test and deploy.
- Prisma schemas live at `prisma/schema.prisma`, `prisma/schema/`, or `db/schema.prisma`; i18n resources in `i18n/` with default locale `ja-JP`; a Chakra theme at `src/theme.ts`.
- Real Node.js must be on `PATH` (not a Bun shim) for Playwright, wrangler, and vinext.
- Plain Next.js apps run Next.js >= 16.3, so `wb start` passes no bundler flag to `next dev` (Turbopack is the default). Blitz apps pin Next.js 15, where the flagless `next dev` selects the webpack dev server that `withBlitz` requires, and wbfy keeps their `typescript` pin below 7 (Next.js 15's `next build` cannot use tsgo).
- macOS and Linux only; Windows is unsupported. A project using `wb db restore` with Turso declares a `libsql:` or `turso:` `DATABASE_URL` and `DATABASE_AUTH_TOKEN`, and has `sqlite3` on `PATH`.

## GitHub-side conventions (WillBooster / WillBoosterLab repositories)

- Squash-only merges with `PR_TITLE` messages, auto-merge enabled, and head-branch deletion on merge.
- A `Protect main` ruleset (WillBooster-owned repositories only, excluding `reusable-workflows`) requires the `test / test` and `semantic-pr / semantic-pr` status checks — plus `test-rust / test-rust` when the repository contains a `Cargo.toml` — and forbids force-pushes and deletion.
- CI calls the organization's own `reusable-workflows` repository (`WillBooster/…` or `WillBoosterLab/…`) at `@main`; repository secrets follow the shared contract (`FNOX_AGE_KEY` for private repositories, `PUBLIC_FNOX_AGE_KEY` for public WillBooster repositories, `TAKUMI_GUARD_TOKEN`, and `VERDACCIO_TOKEN` only for consumers or publishers of `@willbooster-private/*` packages).
- A fixed label taxonomy (`d1`–`d5`, `p1`–`p4`, `r: …`, `s: …`, `t: …`) replaces GitHub's default labels.
- Releases use semantic-release with Conventional Commits; the version field is `0.0.0-semantically-released`.
